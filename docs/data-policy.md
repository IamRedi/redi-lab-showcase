# REDI Lab Data Policy

Document version: 1.0
Date: 2026-09-15
Milestone: REDI-00A
Status: Frozen pending REDI-00A validation

---

## 1. Purpose and Scope

This document defines the data classes, handling rules, access controls, provenance requirements, and publication boundaries for all data processed, stored, or generated by REDI Lab. It applies to:

- All components of the REDI Lab factory (orchestrator, stations, workers, gates, ledger, store, optimizer).
- All Experiment Families A through I.
- All personnel and automated processes that read, write, or transmit REDI Lab data.
- All derived data, whether stored in the Evidence Ledger, Recipe Store, filesystem, or external systems.

The central principle of this policy is: **private project data never becomes training data, never becomes public benchmark data, and never enters a context package without an explicit scope decision that is auditable.**

---

## 2. Data Class Taxonomy

Every piece of data in REDI Lab must be tagged with exactly one primary data class. Subclassifications may be added for granularity, but the primary class determines default handling.

| Class ID | Class Name | Description | Examples |
|---|---|---|---|
| **D01** | Public Synthetic Research Data | Artificially generated task/product specifications and test fixtures created explicitly for REDI Lab research, with no real-world confidential content. | Synthetic Todo REST API spec; synthetic business website order; generated hidden test suites for Tier-1 products. |
| **D02** | Public Benchmark Data | Task datasets, evaluation harnesses, and reference solutions from public third-party software-engineering benchmarks, used under their respective licenses. | SWE-bench subsets; HumanEval-derived tasks; any benchmark with a documented public license. |
| **D03** | Public Repository Data | Source code, documentation, and issue data from publicly accessible software repositories, used under their respective open-source licenses. | A GitHub public repo's issue tracker; open-source packages fetched as dependencies. |
| **D04** | Private Repository Data | Source code, documentation, configuration, and issue data from private repositories or non-public codebases, including any code produced for internal REDI Lab development that is not yet publicly released. | A private GitHub repository accessed for Tier-3 experiments; REDI Lab's own unreleased source code. |
| **D05** | Customer / Project Code | Source code, specifications, configuration, infrastructure definitions, and business data provided by or for a specific customer project or commercial engagement, whether or not the codebase itself is public. | Code produced for a paying client; a product order with proprietary business constraints. |
| **D06** | Prompts and Context Packages | System prompts, station/task prompts, context-compiler output, ContextManifests, and the exact assembled context packages sent to workers. | StationContract system prompt; a compiled context package for a Builder node; a Reviewer gate prompt with criteria. |
| **D07** | Model Outputs | Raw outputs produced by workers, reviewers, or the orchestrator via model API calls, before any post-processing or validation. | Builder node source-code diff; Reviewer node review text; Orchestrator DAG revision text. |
| **D08** | Execution Traces | Low-level worker execution traces: tool call sequences, tool arguments, tool return values, step-by-step reasoning traces (if exposed by the provider), intermediate state transitions, and raw provider response payloads. | OpenAI Agents SDK trace; provider-side step log; tool-call argument/return-value log. |
| **D09** | Metrics and Normalized Evidence | Structured RunEvidence records, GateResult records, ExperimentManifest-specified measurements, aggregated statistical outputs, and normalized ledger entries. | Verified success flag; token counts; cost totals; failure taxonomy codes; Pareto-frontier data points. |
| **D10** | Product Recipes | Versioned ProductRecipe documents stored in the Recipe Store, including DAG templates, worker preferences, context policies, verification policies, evidence-coverage metadata, and validity conditions. | business_web_v1 recipe v3; crud_saas_v1 recipe v1. |
| **D11** | Credentials and Secrets | All authentication material, API keys, access tokens, signing keys, database credentials, TLS certificates, environment-specific secrets, and any string that, if disclosed, could grant unauthorized access to a system or data. | OpenAI API key; GitHub personal access token; database password; signing private key. |
| **D12** | Potentially Publishable Derived Data | Data derived from D04–D05 through an explicit de-identification, aggregation, abstraction, or normalization process such that, to the best of REDI Lab's determination, it can no longer be used to reconstruct the original private source material. | Aggregated per-station success rates across many private projects; normalized task-difficulty categories; high-level recipe topology patterns without concrete code references. |

## 4. What May Enter Model Context

### 4.1 Allowlist Principle
Nothing enters a worker's context package unless it is explicitly permitted by both:
1. The StationContract's owned/allowed scope rules (as enforced by the Context Firewall), AND
2. This data policy's rules for the specific data class.

The Context Firewall is the enforcement point. It must fail closed: if a piece of data's class or provenance is unknown, it is excluded and the exclusion is logged.

### 4.2 Explicit Prohibitions
The following **never** enter any worker or orchestrator model context under any circumstances:
- Any data of class D11 (Credentials/Secrets). See Section 6.
- Raw execution traces (D08) of another worker: only normalized HandoffManifests cross station boundaries.
- Hidden-test content (D01/D02) that is explicitly marked hidden: the Context Firewall must block these, and the hidden-test isolation check (Experiment Policy Section 4) audits the block.
- Any data from a private repository (D04) or customer project (D05) unless:
  - The specific experiment or production run has explicit written approval identifying the scope of private data use, AND
  - The StationContract's scope rules are narrowed to only the explicitly approved subset, AND
  - The resulting ContextManifest is flagged `contains_private_data: true` and is never published as-is (only as D12 if applicable).

### 4.3 Context Reuse Across Runs
A ContextManifest compiled for one production run **may not** be reused as-is for a different product run without re-verifying that:
- The source data (files, contracts) has not changed in a material way; if it has, the hash changes and a new manifest is compiled.
- The scope of the new task matches the scope under which the original manifest was built.

### 4.4 Model-Training Prohibition
**No data of any class collected by REDI Lab may be used for model training, fine-tuning, distillation, or alignment of any third-party model, unless explicitly approved by a REDI-12-or-later governance decision AND compliant with all source data licenses AND compliant with all customer/private-repo agreements.**

This prohibition applies to:
- Using REDI Lab-generated code as training data for a provider's foundation model.
- Sharing prompts, outputs, or traces with a provider for "improvement" purposes unless a written agreement exists and the data is exclusively D01/D02/D03 with compatible licenses.
- Creating derivative training datasets from the Evidence Ledger.

The research target is the production system, not the model. Worker models are interchangeable implementation details behind adapters.

## 5. What May Be Stored

### 5.1 Storage Tiering
REDI Lab data is stored in three tiers, physically or logically separated:

- **Tier 1 — Public Storage**: D01, D02 (per license), D03 (per license), approved D09 metrics from public tasks, approved D10 from public-only recipes, approved D12. May reside on local disk, version-controlled repos, or public object stores.
- **Tier 2 — Internal Private Storage**: All D04 (non-customer private repo), D06/D07/D08/D09 flagged as private-source, D10 learned from private data, unapproved D12 candidates. Must be access-controlled, encrypted at rest, and never pushed to public repositories.
- **Tier 3 — Secret Storage**: D11 exclusively. See Section 6.
- **Tier 4 — Customer-Isolated Storage**: D05 and any data derived from D05 that has not been through D12 release review. Isolated per customer, encrypted, access-controlled with customer-specific credentials, never mixed into cross-customer aggregate analysis unless the D12 process has been completed for each contributing customer's data.

### 5.2 Evidence Ledger Integrity
- The Evidence Ledger (class D09) is append-only. Update and delete operations are prohibited on ledger rows once written. A ledger row may be **marked as invalid** with an explicit invalidation record citing cause (e.g., proven leakage, harness bug), but the original row is retained.
- The ledger's append-only property must be enforced by the storage layer, not only by application logic. (Specific storage technology is deferred to REDI-02; the architectural requirement is set here.)

### 5.3 Cross-Class Contamination
Storage operations must prevent accidental cross-class contamination:
- Private data (D04, D05) must never be written to the same directories, database tables, or object-store prefixes used for public data.
- Backup and disaster-recovery procedures must respect tier separation; a single backup job must not commingle Tier-1 and Tier-4 data without explicit encryption-by-tier and access control.

## 6. Credentials and Secrets (D11)

### 6.1 Non-Negotiable Rules
- **Secrets never appear in prompts, context packages, traces, logs, error messages, source code, Evidence Ledger entries, Recipe Store entries, or ContextManifests.** Any system output that could contain a secret must pass a secret scanner before being stored or transmitted.
- **Secrets never appear in the REDI Lab source repository**, including `.env` files, config files, CI/CD logs, or commit history.
- **Secrets are stored only in a dedicated secret manager** (e.g., OS keyring, dedicated secret-storage service, encrypted per-machine secret store) and are injected into worker runtime environments via environment variables or runtime-vault mechanisms only.
- **Secrets are never passed as tool arguments to workers** in cleartext. If a worker needs to use a secret (e.g., to access a private API), the runtime adapter injects it into the tool's execution environment outside the model's view, and the tool must be separately audited not to echo the secret in its return values.

### 6.2 Secret Lifecycle
- **Issuance**: Secrets are issued per-identity, per-purpose, with the minimum scope and minimum lifetime required for that purpose.
- **Rotation**: Secrets are rotated on a documented schedule and immediately upon any suspected compromise.
- **Revocation**: When a secret is rotated, the old secret is revoked and rendered permanently invalid. Historical live secrets are not retained beyond the audit-log window required to identify compromise timeline.
- **Audit Logging**: Every access to a secret (read, write, rotate, revoke) produces an immutable audit log entry with identity, timestamp, purpose, and outcome. Audit logs are class D04 or D05 as appropriate, never public.

### 6.3 Secret Scan Enforcement
- All ContextManifests are scanned for known secret patterns before the context package is sent to any model. A scan hit aborts the node run and alerts operators; the context package is NOT sent.
- All model outputs (D07) and execution traces (D08) are secret-scanned on ingest. A scan hit quarantines the record and triggers an incident review.
- All commits to the REDI Lab repository are secret-scanned (via pre-commit hooks and CI) before they can be merged.

## 7. What May Be Published

### 7.1 Publication Defaults
Publication of any REDI Lab data or results requires a Release Review (Section 11) unless the data falls entirely within the following pre-approved categories:

**Pre-Approved for Publication (still requires attribution and license compliance):**
1. Class D01 (Public Synthetic Research Data): all synthetic task specs, synthetic hidden tests, synthetic product orders created by REDI Lab.
2. Class D02 (Public Benchmark Data): results on public benchmarks, in accordance with each benchmark's license and disclosure policy.
3. Class D09 (Normalized Evidence / Metrics): per-run metrics and aggregate statistics derived exclusively from D01/D02/D03 tasks, with no private-source contamination.
4. Class D10 (Product Recipes): recipes learned from, and validated exclusively on, D01/D02/D03 tasks.
5. Aggregate statistical outputs from D12-approved derived data, per the D12 approval.

### 7.2 Publication Prohibitions
The following may NEVER be published, regardless of review, unless a legal process (court order, binding regulatory request) compels it and legal counsel has been consulted:
- Any D11 (Credentials/Secrets).
- Any D04 (Private Repo) or D05 (Customer Code) raw data, or any ContextManifest or RunEvidence flagged as private-source, unless the data owner has provided explicit written release consent and the D12 process has been completed.
- Raw execution traces (D08) that include tool arguments, file paths, or model outputs that could reconstruct private code.
- Any data whose publication would violate a third-party license, NDA, or customer contract.

### 7.3 Responsible Benchmark Disclosure
When publishing results on external benchmarks:
- The exact benchmark version, commit, or release date is stated.
- The REDI Lab harness adapter version and any setup differences from the benchmark's standard procedure are described.
- Both positive and negative results on the benchmark are reported (per Experiment Policy Section 15.2).
- The benchmark license and any required attribution are included.

## 8. What Must Remain Private

Data in the following categories must remain private indefinitely, or until explicitly released through the processes in this policy:

1. **All D04, D05, and D11 classes**, as specified above.
2. **All raw execution traces (D08)**, unless and until they pass through a D12 de-identification process and are released.
3. **Any intermediate data, internal reports, or draft analyses** generated during an experiment before the final report, unless the report itself is released.
4. **Unreleased Recipe Candidates** that have not been promoted. Candidate recipes may contain heuristic defaults or hypotheses not yet backed by evidence; publishing them could misrepresent REDI Lab's maturity.
5. **Human intervention records and operator identities**, unless the specific individual consents or the records are required by law.

## 9. Dataset Provenance and License Awareness

Every dataset or input data artifact used in REDI Lab must have a provenance record. The provenance record must include:

### 9.1 Provenance Record Fields
- `dataset_id` and `version`.
- `data_class` (D01–D12).
- `source`: Where the data came from (internal generation, specific benchmark name/version, specific repository URL + commit, specific customer contract reference).
- `license`: Exact license name and version. For internally generated D01/D06, the REDI Lab default license for that data class. For D02/D03, the upstream license text or a URL to it. For D04/D05, the contract reference governing use.
- `attribution_requirements`: Any attribution, copyleft, share-alike, or redistribution clauses from the license, summarized and linked.
- `use_restrictions`: Explicit list of things the license or contract forbids (e.g., "may not be used for model training," "may not be redistributed in modified form"). Enforced by the Context Firewall and storage-tier controls where technically possible.
- `provenance_chain`: For derived data (e.g., a hidden-test suite modified from a public benchmark), a link to the source dataset's provenance record and a description of modifications.

### 9.2 License Compatibility Checks
Before a task dataset or repository is used in any experiment:
- The license is reviewed for compatibility with the intended use case (especially the prohibition on model training in Section 4.4 and any redistribution/publishing intent).
- Any copyleft or attribution requirements are recorded and enforced in downstream publication procedures.
- If the license is ambiguous or the intended use is not clearly permitted, legal review is obtained before the data is ingested.

### 9.3 Provenance Enforcement
- The Context Firewall refuses to include any file in a context package if that file's dataset provenance record is missing or flags the file as out-of-scope for the current experiment.
- The Recipe Store refuses to promote a recipe if any task in its evidence base is missing a provenance record or has a license incompatible with the recipe's intended use.

## 10. Deletion and Retention Expectations

### 10.1 Retention Defaults
The defaults in the class table (Section 3) are minimums. Where legal requirements or customer contracts specify longer retention, those take precedence. Where a shorter retention is legally required or contractually agreed, it is implemented by:
1. Marking the affected Evidence Ledger rows as `data_retention_expired: true` with an expiration timestamp.
2. Deleting or anonymizing the underlying raw data (raw traces, raw outputs, raw context packages) while retaining the normalized, already-measured metric fields and the `expired` marker row as a permanent audit record that the data once existed and was handled under this policy.

### 10.2 Customer-Initiated Deletion
On customer request (for D05), REDI Lab will:
1. Delete all raw customer data, raw outputs, raw context packages, and raw traces within a contractually agreed timeframe.
2. Retain only a minimal, de-identified audit record that the engagement occurred, without any reconstructible content. Whether any aggregated metrics can be retained as D12 is determined on a case-by-case basis with the customer's explicit consent.

### 10.3 Right to Erasure
Requests from individuals (as opposed to customer entities) exercising data-protection rights such as GDPR right to erasure are handled in accordance with applicable law and in consultation with legal counsel. Such requests are logged but do not require deletion of normalized evidence rows that have already been fully de-identified and aggregated to D12 standards, unless the law specifically requires it.

### 10.4 Secure Destruction
When data is deleted at end-of-life or by request:
- The deletion is performed in a manner appropriate to the storage medium (secure overwrite for magnetic media, cryptographic erasure by destroying the encryption key for encrypted storage).
- Backups are included in the deletion scope, or are retained only if legally required, in which case they are marked and access-controlled.
- A deletion record is created with timestamp, scope, authorizing party, and method.

## 11. Preventing Private Code from Becoming Public Dataset Material

This section is non-normative in the sense that it describes additional procedural controls whose exact implementation details may evolve, but the requirement it enforces — that private code does not accidentally become public training data or benchmark data — is normative.

### 11.1 Data Classification at Ingest
Every file, repository, or product order ingested into REDI Lab is classified immediately upon receipt. Classification is not optional. The default classification for any data whose source is not explicitly documented as public D01/D02/D03 is D04 (Private Repo) or D05 (Customer Code). Data is not "innocent until proven public"; it is private until proven public.

### 11.2 Technical Barriers
- **Cross-tier write prevention**: Storage APIs for Tier 1 (public) storage reject writes from processes whose input data includes any D04/D05-class artifacts, unless the write is explicitly tagged as D12 and accompanied by a Release Review ID.
- **Content fingerprinting**: Before any data is moved to Tier 1 or approved as D12, it is checked against a fingerprint database of known private-repo and customer-code content. A fingerprint match blocks the release and triggers review.
- **Diff/similarity review**: For D12 candidates derived from D04 or D05, a human reviewer compares the candidate against the source private material to ensure the candidate does not contain verbatim code snippets, recognizable algorithmic structures, or business logic that would enable reconstruction of the source.

### 11.3 Procedural Barriers
- **Release Review**: Any publication of D12, or any publication that might touch D04/D05 material, requires a documented Release Review with:
  - Identities of reviewers (at minimum one domain expert familiar with the source data's sensitivity, and one person independent of the experiment's investigators).
  - Checklist items covering license, provenance, classification, content reconstruction risk, and contractual obligations.
  - Explicit approval or rejection with written justification, versioned and stored.
- **Public dataset registry**: All datasets released externally are entered into a public registry with classification, provenance, license, release-review reference, and a statement that the dataset contains no private material or has been cleared through D12.
- **Training-use prohibition enforcement**: Any external dataset release explicitly states whether it may be used for model training. The default for D12 is **no training use permitted** unless a separate governance decision explicitly opts in, and even then only after license and contract review.

### 11.4 Incident Response
- Any suspected incident of private data entering public storage, being published externally, or being shared with a model provider for training purposes is treated as a security and data-governance incident. Response includes:
  1. Immediate containment: remove the data from public access, rotate any exposed secrets, notify affected parties.
  2. Investigation: determine scope, root cause, impact.
  3. Remediation: correct the procedural or technical gap that allowed the incident.
  4. Documentation: incident report, impact assessment, corrective action plan, all stored in the private governance record.
  5. Notification: notify affected customers, data subjects, and authorities as required by law and contract.

## 12. Derived Data Release Procedure (D12 Path)

Data derived from D04 or D05 may be elevated to D12 and published only by completing the following steps:

1. **Derivation**: The candidate derived data is generated by a documented, versioned algorithm that performs aggregation, abstraction, or de-identification. The algorithm's source and its input/output mapping are versioned under the experiment's governance.
2. **Non-Reconstruction Test**: A qualified reviewer (independent of the data's originator) attempts to reconstruct private source material from the candidate. Reconstruction is defined as:
   - Recovering verbatim code snippets of N lines or more, evaluated on the basis of source recoverability and proprietary-information risk. A **provisional internal safety default of 5 contiguous non-trivial lines** may be used as a starting review trigger during REDI-01 implementation and pilot work, pending validation. This numeric default is a data-release process safeguard, not a scientifically established universal threshold, and does not on its own determine release approval. The reviewer's qualitative judgment of source recoverability and proprietary-information risk takes precedence over any line-count heuristic.
   - Recovering recognizable proprietary business logic, pricing structures, customer identities, or security-sensitive configuration.
   - Linking an aggregate record back to a specific private project or individual.
   If reconstruction succeeds or is plausible, the candidate is rejected.
3. **License and Contract Review**: The derivation is confirmed compliant with all upstream licenses and customer contracts.
4. **Release Review**: Per Section 11.3, with sign-off recorded.
5. **Versioning**: The approved D12 artifact is assigned an ID, version, and release timestamp. Its provenance chain links back to the source D04/D05 dataset IDs (by reference, not by content) so auditors can trace lineage, while the content remains de-identified.
6. **Ingest**: The artifact is written to Tier 1 storage and registered as D12, with its Release Review ID and non-reconstruction test result IDs attached.

## 13. Compliance Monitoring

- Periodic audits (minimum annually, or more frequently if required by customer contracts or law) verify that:
  - Data class tags are correctly assigned.
  - Storage tiers are correctly used.
  - Secret-scan enforcement is active and has no known bypasses.
  - Deletion requests have been executed.
  - Publication releases have corresponding Release Reviews.
- Audit findings are documented in a private governance record. Material non-compliance triggers corrective action, which may include freezing all publication and model-provider data-sharing until the gap is closed.
- Any employee or contractor found to have knowingly violated this policy in a manner that risks private-data disclosure is subject to disciplinary action up to and including termination and, where appropriate, legal referral.
